# 런북

## 시험 한 명령씩
| 명령 | 내용 |
|---|---|
| `bash scripts/setup-env.sh` | 환경 준비(Node/npm 점검 + `npm ci`, 리포 안 `node_modules`) |
| `npm test` | 단위·계약 시험(doctor 판정 시험 포함. jsdom 시험은 호스트에 jsdom이 없으면 건너뜀) |
| `npm run typecheck`, `npm run check-schema` | 타입, 스키마 열거값 |
| `npm run smoke` | 이미지 빌드, `/healthz`, 라벨, non-root (Docker 필요) |
| `npm run test:dom` | 기록 보기 DOM 시험(jsdom, node 컨테이너) |
| `npm run test:e2e` | 실제 헤드리스 Chromium 화면 흐름. Playwright 공식 이미지 안에서 돈다(아래) |
| `npm run doctor` | 전제 점검: Docker 명령과 데몬. 없으면 `FAIL: 전제 미충족`, 종료 코드 1 |
| `npm run test:e2e:host` | 선택 사항. 호스트에 설치된 브라우저로 직접 실행(아래) |

## 브라우저 시험(`test-e2e/`) 전제
전제는 Docker 하나다(데몬 접속 가능, `npm run doctor`로 점검. `smoke`와 같은 전제). 호스트에 브라우저, 시스템 라이브러리, 글꼴을 설치하지 않는다.
`npm run test:e2e`는 `scripts/e2e-docker.sh`가 `test-e2e/Dockerfile`로 이미지를 만들어 실행한다.
- 베이스: `mcr.microsoft.com/playwright:v1.55.1-noble`(익명 pull). 태그는 `package.json`의 playwright 버전(1.55.1)과 같아야 한다. 올릴 때 둘을 함께 바꾼다.
- 얇은 층: node 24(리포 엔진 요구, 이미지 기본은 22), `fonts-noto-cjk`(공식 이미지는 한국어 전용 글꼴이 없어 `fc-list :lang=ko`가 중국어·유니폰트뿐이다). 컨테이너는 시작 때 Noto CJK가 있는지 확인한다.
- non-root(pwuser)로 실행, `--init --ipc=host`(Playwright 문서 권장). 모의 서버와 정적 서버는 컨테이너 안의 빈 포트이고 호스트 포트를 열지 않는다. 이미지와 컨테이너 이름에 리포 이름과 PID를 넣어 동시 실행해도 충돌하지 않는다.
- 스크린샷은 컨테이너에서 `e2e-artifacts/`(gitignore)로 복사된다. 환자 정보 없는 가짜 문장만 쓴다.
- 시험은 새 헤드리스 모드(`channel: "chromium"`)를 쓴다. headless shell은 알림 권한 부여가 동작하지 않는다.

`npm run test:e2e:host`(선택): `npm ci`, `npx playwright install chromium`, 필요하면 `sudo npx playwright install-deps chromium`, `sudo apt-get install -y fonts-noto-cjk`가 필요하다. `doctor --host`가 부족한 라이브러리 이름과 글꼴 없음을 안내만 한다(FAIL 아님, 글꼴은 시험 통과와 무관). 표준 경로는 컨테이너 방식이다.

### 검증 환경과 한계
브라우저 시험 통과는 이 작업 PC에서 `npm run test:e2e`(Docker 컨테이너, Playwright 1.55.0 공식 이미지, 우회 없음, 호스트 설치 없음)로 확인했다. 컨테이너 안에서 한글 글꼴(Noto CJK)로 스크린샷의 한글이 정상 표시되는 것도 확인했다. 호스트 직접 실행(`test:e2e:host`)은 이 PC에서 돌려 보지 못했다(sudo 암호가 필요해 시스템 라이브러리를 설치할 수 없다). 이 시험은 모의 서버와 헤드리스 Chromium이고 실제 기기·마이크·푸시 서비스가 아니다.

### 자동으로 확인하는 것
직원 콘솔 기록 보기(알림 → 기록 보기 → 대화·값·알림 표시 → 확인 단계를 거친 재개 → 닫기/Esc)는 브라우저 시험에 있고, 렌더 세부(빈 turns, null 필드, 404·권한·네트워크 오류 문구, 닫을 때 발화 삭제)는 `npm run test:dom`(node 컨테이너, jsdom)이 확인한다.

시작 → 질문 → 텍스트 제출 → 다음 질문 → 종료, 가짜 SpeechRecognition 경계(ko-KR 어댑터가 텍스트를 서버로 전달), 위험 발화 대기 화면, 직원 호출 화면(알림 전달 실패)과 처음으로, 503 지속 시 재시도 대기 화면(직원 부르기·그만하기) 뒤 직원 호출 화면, 재시도 중 직원 부르기, 저장 실패 시 다시 말하기, 지연 중 대기 화면, 직원 콘솔 실시간 알림과 이어서 진행(키오스크가 폴링으로 재개), 서비스 워커 등록·활성화와 푸시 핸들러의 알림 표시(합성 PushEvent).

### 사람 확인 필요(구멍) 체크리스트
실제 기기·실제 브라우저(Chrome, 키오스크 단말)에서 사람이 한다.
- [ ] 직원 콘솔 기록 보기: 실제 survey-service에 붙였을 때 `GET /v1/staff/sessions/{id}` 응답이 화면에 맞게 나오는지(모의 서버로만 확인했다), 스크린 리더로 읽히는지.
- [ ] 마이크 권한 요청 창이 뜨고, 허용하면 "말하기" 버튼이 듣기 상태가 된다. 거부하면 텍스트 입력 또는 다시 말하기로 이어진다.
- [ ] 한국어 STT 정확도: 실제 음성으로 증상 문장 10개 이상을 말하고 인식문과 신뢰도(confidence)를 기록한다. `MIN_CONFIDENCE`(0.4) 적정성 판단. 소음 환경 포함. (Web Speech API는 Chrome에서 인터넷 연결과 구글 음성 서비스에 의존한다.)
- [ ] 인식 결과가 비었을 때(침묵) "다시 말씀해 주세요"가 나온다.
- [ ] TTS(ko-KR) 음성이 나오고 알아들을 만하다. 단말에 한국어 음성이 설치되어 있는지.
- [ ] 단말에서 한글 글꼴이 정상 표시되고 글자 크기가 읽기 쉽다(실물 화면 해상도).
- [ ] 웹 푸시 구독: 직원 콘솔에서 "푸시 알림 켜기" → 알림 권한 허용 → 구독 성공. 헤드리스 시험은 구독 단계에서 `Registration failed - permission denied`로 실패한다(Chromium의 푸시 구독은 외부 푸시 서비스에 의존하고 자동화 환경에서는 허용되지 않는다). 구독 객체 생성은 확인하지 못했다.
- [ ] 실제 푸시 서비스(FCM 등)를 거친 서버 → 브라우저 전달, 브라우저를 닫았거나 화면이 꺼진 상태의 알림 표시, 알림 클릭 시 `/staff/` 열림. VAPID 키가 설정된 실제 서버 필요.
- [ ] HTTPS 배포 환경에서 서비스 워커 등록(시험은 127.0.0.1 http, 보안 컨텍스트로 취급됨).
- [ ] 실제 survey-service와의 연동(시험은 모의 서버).

### STT 경계
`src/components/stt_adapter.ts`의 `SttAdapter`가 경계다. `SpeechRecognition`이 없으면 텍스트 입력으로 대체되고, 시험은 가짜 `SpeechRecognition` 주입(`addInitScript`)으로 어댑터 경로를 지난다. 마이크 입력과 인식 자체는 가짜로 대체된 것이다.

## 키오스크 화면별 대응 (감사 P11)
| 화면 | 뜻 | 운영자 조치 |
|---|---|---|
| "직원을 불러 주세요" | 재시도 예산(24초) 소진·인증 거부·토큰 없음·접수 정보 오류·다시 말하기 상한(3회)·환자가 직원 부르기를 누름 | 환자를 돕고 "처음으로"(서버 세션 종료를 시도한다. 알림 전달 실패 때는 확인 단계가 있고 세션은 종료하지 않는다 — 직원 콘솔에서 그 세션을 확인). 반복되면 gateway `/readyz`, survey-service 상태, 기기 토큰을 확인 |
| "직원이 곧 도와드립니다"(위험 정지 대기) | 세션이 PAUSED_RISK. 직원 콘솔에 알림이 열려 있어야 한다 | 직원 콘솔에서 이어서/종료 결정. "상태를 확인하지 못하고 있어요"가 보이면 서버 연결 장애: 직원이 직접 환자에게 간다 |
| "종료를 서버에 알리지 못했습니다" | 종료 요청이 서버에 닿지 않았다(열린 세션이 남았을 수 있다) | 직원 콘솔에서 해당 세션을 확인. 서버는 유휴 만료로 정리한다 |
| 첫 화면 아래 "접수 정보 없이 시작했습니다" | 환자 참조를 받지 못했다(한 번 쓴 참조는 다시 쓰지 않는다) | 접수 연동을 확인. 새 URL 조각을 환자마다 보내야 하는지는 사용자 확인 대기 |
| 브라우저 기본 오류 화면 | 정적 서버/gateway 장애로 새로고침·최초 로드 실패 | gateway와 이 이미지(`/healthz`)를 확인. 이미 열린 화면은 정적 서버 장애와 무관하게 이어진다 |
| 직원 콘솔 머리줄 "연결 끊김" | 알림 스트림 끊김. 자동 재연결 중 | 15초 안에 돌아오지 않으면 네트워크·gateway 확인. 그동안 목록은 15초마다 새로 읽는다 |
정적 서빙(Caddy) 로그는 표준 출력 한 줄 JSON이며 `/healthz`·`/readyz`와 요청 헤더·쿼리 문자열은 남기지 않는다. 회전은 컨테이너 런타임(Docker 로그 드라이버 `max-size`) 몫이다(감사 P22).

## 기기 토큰과 환자 참조 (D85)
- 키오스크 시작 URL 예: `https://<병원 호스트>/#device=<기기 토큰>&subject_ref=<접수가 넘긴 참조>`. 값은 조각(`#`)으로만 넘긴다(쿼리 문자열은 서버 로그에 남는다). 앱이 읽는 즉시 주소창에서 지운다. 새로 고치면 조각이 사라지므로 기기 토큰은 기기 설정 `/config.json`(`{"device_token": "..."}`, 게이트웨이나 기기 배포가 내는 정적 파일)에 두는 것이 안전하다. 조각이 설정보다 먼저다.
- 화면 증상(계약 2.3.0부터 기기 인증은 게이트웨이 mTLS이고 앱은 자격을 보내지 않는다, ADR 0024): "이 기기의 인증이 거부되었습니다" = 서버·게이트웨이가 401·403(인증서 문제 또는 2.x 토큰 방식의 토큰 폐기·오타). "설정이 필요합니다" 화면은 없어졌다. "접수 정보를 확인할 수 없습니다" = subject_ref 형식 오류(1~128자 `[A-Za-z0-9._:/#=+-]`) 또는 서버 필수 설정에서 값 누락. 모두 직원 호출 화면이다.
- (2.x 호환, 3.0.0에서 삭제) 기기 토큰 보관(D88 U8): 권장 경로는 `/config.json`이다. 정적 서버는 `CONFIG_FILE`(운영이 파일로 마운트한 기기 설정, 예: `{"device_token": "...", "allow_remote_stt": false}`)을 `/config.json`으로 내므로 새로고침해도 유지되고 브라우저 저장소를 쓰지 않는다. 토큰은 기기별로 발급하고(서버가 기기별 토큰을 받는다는 점은 survey-service 작업이며 이 영역은 확인하지 못했다) 이 파일은 그 기기에서만 읽히게 gateway가 막아야 한다. `#device=` 조각은 새로고침하면 사라지는 시연용이다. localStorage·쿠키에 영구 저장하는 방식은 만들지 않았다: 공유 PC에서는 다음 사용자가 읽을 수 있고 XSS 시 유출되므로, 기기 전용 브라우저 프로필이 보장될 때만 검토하며 그 경우에도 위험을 문서화해야 한다.
- 모의 서버로 시연(mTLS 흉내): `MOCK_GATEWAY_DEVICE=kiosk-01 STATIC_DIR=dist node mock-server/main.ts`. 2.x 토큰 방식은 `MOCK_DEVICE_TOKEN=<가짜 값> MOCK_REQUIRE_SUBJECT_REF=1 STATIC_DIR=dist node mock-server/main.ts`. 토큰 값을 로그에 쓰지 않는다.
- 토큰·환자 참조는 로그·콘솔·스토리지에 남기지 않는다(`test/d85.test.ts`와 브라우저 시험이 확인한다).
