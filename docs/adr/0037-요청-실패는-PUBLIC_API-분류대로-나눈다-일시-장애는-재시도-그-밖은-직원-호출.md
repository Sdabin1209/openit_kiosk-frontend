# 0037. 요청 실패는 PUBLIC_API 분류대로 나눈다: 일시 장애는 같은 turn_id로 재시도, 그 밖은 재시도 없이 직원 호출 화면

- 상태: 채택 (2026-11-04, 계약 3.4.6 반영)
- 맥락: 계약 PUBLIC_API "프론트가 지킬 것"과 RUNTIME R3.13·R3.20·R3.21·R10.6이 키오스크의 실패 처리를 정했다. 이전 구현은 409를 직원 대기 화면으로, 404를 처음 화면으로, NOT_COMMITTED 응답을 "다시 말씀해 주세요" 화면으로 보냈다. 계약과 달랐다.
- 결정: (1) 재시도하는 것: 408·429·502·503·504, 네트워크 오류와 무응답, 409 `TURN_IN_PROGRESS`, 그리고 200이지만 `turn_failure_signal.write_committed=NOT_COMMITTED`(위험 정지 신호 `staff_alert` DELIVERED·DELIVERY_FAILED가 없을 때만). 모두 같은 `turn_id`, 지수 백오프+지터, 총 예산 120초(ADR 0035). 예산을 넘기면 직원 호출 화면(`RETRY_EXHAUSTED`). (2) 재시도하지 않는 것: 400·403·404·409(`TURN_IN_PROGRESS` 제외)·413·414·422·431과 500은 직원 호출 화면이다. 401·403은 사유가 `AUTH`다. 다음 환자는 새 세션으로 시작한다. (3) 시작 때 503 `NO_ACTIVE_RELEASE`는 재시도 루프에 넣지 않고 시작 불가 안내(`NOT_OPEN`)를 보인 뒤 `Retry-After`(없으면 1초) 뒤 목록을 다시 받는다. 환자가 "처음으로"를 누르거나 유휴 시간이 지나면 멈춘다.
- 왜: 계약이 정했다(PUBLIC_API, RUNTIME R3.13·R3.20, RFC 9110 15.5.9 408, 15.5.14 413, 같은 요청은 같은 결과라 재시도해도 소용없는 응답은 재시도하지 않는다). NOT_COMMITTED는 확정되지 못한 턴이라 서버가 같은 `turn_id` 재전송을 다시 처리한다(PUBLIC_API, D86). 위험 정지 신호가 있으면 안전 판단(직원 호출)이 저장 재시도보다 먼저다. 값(120초 등)은 새로 만든 것이 없고 ADR 0035를 따른다.
- 검토한 대안: (1) 409를 직원 대기로 두기 -> 계약은 직원 호출 화면이다. (2) NOT_COMMITTED를 환자에게 "다시 말씀해 주세요"로 돌리기 -> 같은 발화를 환자가 다시 말하게 하고 `turn_id`가 바뀌어 중복 처리 위험이 생긴다.
- 결과: 얻는 것 - 계약과 같은 실패 화면, 일시 장애가 환자 조작 없이 풀린다. 감수하는 것 - 404(세션 만료)도 직원 호출 화면이 된다(예전에는 처음 화면). 저장 실패가 계속되면 최대 120초 뒤에야 직원 호출이다(환자는 재시도 중 화면에서 직원을 부를 수 있다).
- 되돌리는 조건: 계약 PUBLIC_API의 분류가 바뀌면 새 ADR로 대체한다.
