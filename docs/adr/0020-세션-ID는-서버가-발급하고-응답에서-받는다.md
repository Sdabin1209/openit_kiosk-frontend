# ADR 0020: 세션 ID는 서버가 발급하고 시작 응답에서 받는다

## 상태
채택됨 (2026-10-29, 단계 B, 계약 2.2.0 D106). 이전에는 키오스크가 `"s-" + 24자리 hex`를 만들어 보냈다(표준성 점검 #17의 방식).

## 맥락
계약(`../boundary-contracts/PUBLIC_API.md` 원칙 절)이 세션 ID를 서버 발급으로 바꿨다. `POST /v1/sessions`에서 `session_id`를 생략하면 서버가 CSPRNG로 만든 값을 응답의 `session_id`로 돌려준다. 프론트가 보내는 방식은 2.x에서만 허용되는 폐기 예정 방식이고 3.0.0에서 제거된다.

## 결정
- 시작 요청 본문은 `{kind: "SESSION_START", subject_ref?}`뿐이다. 세션 ID를 만드는 코드(`newSessionId`)를 없앴다.
- 시작 응답은 `FrontendInput`에 `session_id`를 더한 모양으로 검사한다(`validateSessionStarted`). `session_id`가 없거나 1~64자 영문·숫자·`-_`가 아니면 지어내지 않고 잘못된 본문으로 보아 5xx와 같이 재시도하고, 예산을 넘으면 직원 호출이다.
- 키오스크는 응답의 ID를 이후 모든 호출(발화, 종료, 상태, 재알림)에 쓴다. 시작 요청은 ID가 없어 세션별 직렬 큐 밖이고, 이후 요청부터 그 ID로 큐가 생긴다.
- 시작이 아직 응답을 못 받은 재시도 중에 '그만하기'를 누르면 서버가 준 ID를 모르므로 종료 요청을 보낼 수 없다. 요청을 끊고 종료 화면으로 간다.
- 모의 서버는 `session_id`가 없으면 `crypto.randomBytes(16)`의 base64url(22자)로 발급해 응답에 싣는다. 보내는 옛 방식은 2.x 호환으로 그대로 받는다.

## 왜 (따른 표준과 근거)
- 계약 2.2.0이 정했다. 계약의 근거는 OWASP 세션 관리 권고(예측할 수 없는 값은 서버가 만든다)이고 계약 문서도 "원문 대조 전"이라 적었다. 이 영역은 그 판단을 따를 뿐 따로 표준 비교를 하지 않았다.

## 검토한 대안과 버리는 이유
- 옛 방식 유지: 계약이 폐기 예정으로 못박았고 3.0.0에서 제거된다.
- 시작 재시도 중 그만하기에서 서버에 종료 요청 보내기: ID를 모르므로 불가능하다.

## 결과
- 얻는 것: 클라이언트가 ID를 만들지 않는다.
- 감수하는 것: (1) 시작 요청이 시간 초과 등으로 응답을 못 받고 같은 요청을 재시도하면, 서버에 이미 만들어진 세션과 별개로 새 세션이 생길 수 있다(시작에 멱등 키가 없다). 남은 세션은 서버 유휴 만료가 정리한다고 보지만 서버 쪽은 확인하지 못했다. (2) 문진 스키마(survey-service 소유)와 계약 문서가 어긋난다: `FrontendMessage`(SESSION_START)는 아직 `session_id`를 required로, `FrontendInput`은 `additionalProperties:false`로 `session_id` 필드를 두지 않는다. 이 영역의 시험은 시작 본문을 계약 문장으로 확인하고 응답의 `session_id`를 뺀 나머지를 스키마로 검사한다. 정리는 헤드/survey-service 몫이다. (3) 응답의 `session_id` 위치를 계약 문장("응답의 session_id")에 따라 최상위로 읽었다. 스키마가 없어 확인하지 못했다.

## 되돌리는 조건
계약이 응답 모양을 바꾸면(예: 별도 시작 응답 스키마) `validateSessionStarted`만 고친다.
