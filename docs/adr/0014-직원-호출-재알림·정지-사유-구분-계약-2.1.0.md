# ADR 0014: 직원 호출 재알림·실패 기록과 정지 사유 구분 (계약 2.1.0, CR-H001·CR-H002)

## 상태
채택됨 (2026-10-28). 화면 문구는 모두 **provisional(임상 검토 필요)** 이다. 계약 `boundary-contracts` 2.1.0 스펙(86da3bf)을 작업 트리 기준으로 구현했고, 태그 v2.1.0은 아직 받지 못했다(받으면 의존을 올리고 재시험한다).

## 맥락
`staff_alert = DELIVERY_FAILED`이면 키오스크는 직접 알리라고 안내하는 데서 멈췄고, 알림을 다시 보내거나 "닿지 않았다"를 서버에 남길 길이 없었다(ADR 0004의 "직원 호출 화면의 처음으로" 절). 위험 정지와 되묻기 한도 정지는 같은 `PAUSED_RISK`라 키오스크·직원 콘솔이 구분하지 못했다. 헤드가 CR-H001·CR-H002를 채택했다. 직원 콘솔(`apps/staff`)은 이 영역 소유이므로(admin-console에 직원 알림 화면 없음, 헤드 확인) 콘솔 표시도 이 영역이 한다.

## 결정
1. **다시 부르기**(`POST /v1/sessions/{id}/staff-call/retry`, 본문 `{turn_id}`): `CALL_STAFF`(DELIVERY_FAILED)에서만 버튼을 보인다. 응답의 `retry_after_s` 동안 버튼을 비활성(카운트다운)한다. `DELIVERED`면 위험 정지 대기 화면(상태 폴링)으로 바꾼다. 여전히 `DELIVERY_FAILED`면 화면에 남고 다시 센다. 호출 클라이언트는 **자동 재시도하지 않는다**(`CallOptions.single`): 429는 일시 장애가 아니라 "너무 일찍/상한"이라는 답이기 때문이다.
2. **실패 기록**(`.../staff-call/report`, `{outcome, turn_id}`): 기존 '직원에게 직접 알리셨나요?' 확인 단계와 연결한다. '직접 알렸어요, 처음으로' -> `STAFF_NOTIFIED_MANUALLY`, '취소'(아직 못 알림) -> `NOT_NOTIFIED`. 기록은 최선 노력이다. 실패해도 환자를 화면에 가두지 않는다.
3. **turn_id 규칙**(헤드 결정): 응답을 받은 호출 다음은 새 `turn_id`. 응답을 못 받은(시간 초과·네트워크) 재전송은 같은 `turn_id`(서버 멱등, 시도 횟수 증가 없음). report는 같은 `turn_id`에 다른 `outcome`이 409이므로 항상 새 `turn_id`.
4. **환자 안전 규칙**(헤드 결정): report가 `NOT_NOTIFIED`여도, retry가 429 `RETRY_LIMIT` 또는 409 `NO_OPEN_ALERT`여도 직원 호출 화면을 **끝내지 않는다**. 환자가 세션을 임의로 끝내지 못하는 기존 규칙(직원 개입으로만 해제)을 유지한다. 화면은 "접수처로 직접 가서 직원에게 알려 주세요"를 계속 크게 보이고, 버튼은 서버가 허용하는 동안(`retry_after_s` 지난 뒤, 상한 전)에만 켠다. 상한 도달·열린 알림 없음이면 버튼이 사라지고 직접 안내만 남는다.
5. **기능 감지**: retry/report가 404/405이면 그 세션 동안 기능을 끄고 기존 동작('직접 알리셨나요?'만)으로 물러난다(CR-H001 5절, PUBLIC_API.md G절 호환). 사전 탐지용 안전한 호출이 없어 **첫 사용 때 감지**한다. 한계: 404는 "다른 기기의 세션"일 때도 나오므로 구분하지 못한다. 어느 쪽이든 직접 안내가 남으므로 안전한 쪽으로 기운다.
6. **pause_reason**: 키오스크는 `/state` 폴링에서 읽는다(`RISK|REASK_LIMIT|OTHER`, 모르는 값 OTHER, 없으면 미상: PUBLIC_API.md H절). 환자 화면은 **서버 고정 문장(`response_text`)을 항상 우선**한다. 문장이 없고 사유가 `REASK_LIMIT`일 때만 `REASK_LIMIT_WAIT_NOTICE`를 보인다(위험 정지 기본 문구와 다르고 "위험하지 않다"는 단정은 하지 않는다). 사유는 `body[data-pause-reason]`로도 노출한다. 직원 콘솔은 알림 목록·세션 기록에 **글자 접두**("[위험 정지]", "[되묻기 한도 정지]", "[정지: 그 밖의 사유]")와 전달 시도 횟수·마지막 전달 상태·환자 직접 통지 보고를 보인다. 색·테두리 모양은 보조일 뿐이다.

## 왜 (근거, 따른 표준)
- 구조와 값은 계약 PUBLIC_API.md G·H절과 CR-H001·H002에서 왔다. 이 영역이 정한 값은 없다. **재알림 간격 30초·상한 10회는 서비스 설정이며 키오스크에 박지 않는다**: 버튼 비활성 시간은 항상 응답의 `retry_after_s`(또는 429 `Retry-After`)에서 온다.
- 자동 재시도 제외: 서버 간격 하한을 키오스크 재시도가 두드리면 상한만 소모한다. 429 `Retry-After`를 존중하는 것은 HTTP 표준(RFC 9110 10.2.3)이다.
- 접근성: WCAG 2.2 — 2.2.1(시간 제한 조정) 안내 문장은 사라지지 않고 카운트다운은 버튼 활성 여부일 뿐 환자 입력의 시간 제한이 아니다. 1.4.1(색에만 의존 금지) 정지 사유는 글자로 구분. 2.1.1(키보드) 모든 버튼은 `button`. 4.1.3(상태 메시지) 안내 문장은 `role=status`이고, 1초마다 바뀌는 숫자는 `aria-hidden` 요소에 두어 낭독기가 매초 읽지 않게 한다. 초점은 CALL_STAFF에 처음 들어올 때만 옮긴다.
- 카운트다운은 `setTimeout`을 주입 가능한 `timers`로 돌린다(기존 유휴 타이머와 같은 방식): 시험이 가짜 시계로 결정적이다.

## 검토한 대안과 버리는 이유
- 재알림을 발화 재전송으로 유도: 위험 선별이 세션·턴 기준 멱등이라 새 알림이 안 생긴다(CR-H001 4절).
- 429를 기존 재시도 정책(ADR 0004)에 맡김: 버튼을 막은 카운트다운과 이중으로 돌아 상한을 소모한다. 그래서 `single` 옵션.
- NO_OPEN_ALERT를 "직원이 처리함"으로 보고 대기 화면으로 보냄: 키오스크는 어느 쪽인지 모른다. 환자 안전 쪽으로 기울여 화면을 유지한다(헤드 결정). 대기 화면의 상태 폴링은 환자가 계속 볼 수 있는 길이지만 이번엔 쓰지 않는다.
- 새 REASK_LIMIT 문구 없이 기존 문구 재사용: 위험 정지 문구를 되묻기 정지에 쓰면 환자에게 오해를 준다. 단 서버 고정 문장이 있으면 그것이 우선이므로 새 문구는 서버가 문장을 안 줄 때의 안전망이다.
- 사유를 색으로만 구분: 1.4.1 위반.

## 결과
- 얻는 것: 전달 실패가 서버 기록에 남고(환자 보고), 환자·현장이 다시 부를 수 있으며, 직원 콘솔이 "전달 실패"와 "되묻기 한도"를 눈에 띄게 본다.
- 감수하는 것: 문구는 모두 임시(provisional, 임상 검토 전: `apps/kiosk/clinical.ts`의 `REASK_LIMIT_WAIT_NOTICE`, `DELIVERY_FAILED_DIRECT_NOTICE`, `STAFF_CALL_NOTICES`). 기능 감지가 첫 사용 때 일어난다. 실제 survey-service와는 연동 시험을 하지 않았다(모의 서버만; 모의 서버 응답은 계약 스키마로 검사). `StaffAlertPage` 스키마가 새 필드를 거부하던 결함은 계약 2ec2849에서 고쳐졌다.
- 측정하지 않은 것: 현장 재알림 간격에서의 환자 행동, 카운트다운 길이에 대한 사용성, 실기기 낭독기 동작.

## 독립 검토 반영 (4426b7b 재현 결함, 같은 날 추가)
- **M-1 재전달 판정**: 서버는 재알림을 새 이벤트 이름 없이 같은 `alert_id`의 `alert` 이벤트로 보낸다. 직원 콘솔은 목록에 있는 열린 알림의 `delivery_attempts`가 **커졌을 때만** 재전달 배너를 낸다(목록은 한 건으로 합침). 왜: 계약에 전달 시각 필드가 없고 시도 횟수만 단조 증가하는 신호다. Last-Event-ID 이어받기로 다시 오는 오래된 이벤트는 같거나 작은 번호라 조용히 넘기고 저장값도 되돌리지 않는다. 푸시는 `renotify: true`: 같은 tag는 그것 없이는 소리·진동 없이 조용히 교체된다. 한계: 필드를 보내지 않는 옛 서버는 재전달을 알 수 없다. 실제 푸시 소리는 헤드리스에서 확인하지 못했다(사람 확인).
- **M-2**: 재알림 401/403은 `callStaffReason`을 유지하고 안내만 바꾼다(AUTH 화면으로 가면 직접 안내와 확인 단계가 사라져 한 번 누름으로 떠날 수 있었다).
- **M-3**: 응답을 받은 것으로 보는 상태는 200/409/429/404/405/401/403이다. 500/502/503/504·네트워크·시간 초과는 서버가 처리했는지 모르므로 `turn_id`를 유지한다(서버 멱등).
- **M-4**: 409는 `details.reason`을 본다. `NO_OPEN_ALERT`만 버튼을 끄고, `TURN_IN_PROGRESS` 등은 일시 충돌로 보고 Retry-After(없으면 2초) 뒤 다시 누르게 한다. 404/405는 옛 서버·세션 없음·다른 기기를 키오스크가 구분할 수 없으므로 "지금은 쓸 수 없음"까지만 말하고 직접 안내를 남긴다(안전 방향).
- **L-1/L-2**: report 진행 중 확인 단계 버튼을 잠가 더블 클릭이 한 번만 나가게 한다. 응답을 못 받았으면 같은 `turn_id`로 최대 2회(`REPORT_ATTEMPTS`, 임의 값, 측정 안 함) 보내고 실패해도 환자를 가두지 않는다.
- **L-3**: 확인 단계를 연 사이 늦은 DELIVERED가 오면 대기 화면으로 간다. 직원에게 닿았다는 사실이 더 안전한 쪽이라 유지하고 시험으로 고정했다.
- **L-4**: 카운트다운이 끝나는 순간 `role=status` 안내("다시 부르기를 누를 수 있습니다")를 싣고 초점을 버튼으로 돌린다(WCAG 2.4.3 초점 순서, 4.1.3). 카운트다운 숫자는 계속 낭독하지 않는다.

## 되돌리는 조건
임상 검토에서 문구가 바뀌거나, 재알림 정책(간격·상한·NOT_NOTIFIED 뒤 동작)이 현장 흐름으로 정해지면 `clinical.ts`와 이 ADR을 새 ADR로 대체(Supersedes)한다. 계약이 retry/report를 바꾸면(MAJOR) 기능 감지와 함께 재검토한다.
