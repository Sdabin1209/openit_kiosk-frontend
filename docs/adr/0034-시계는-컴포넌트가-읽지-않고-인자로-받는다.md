# 0034. 시계는 컴포넌트가 읽지 않고 인자로 받는다

- 상태: 채택 (2026-10-31, 헤드 지시 U422). 0033의 값(대기 12초, 예산 24초)은 그대로이고 그 값이 시험에서 확인되는 방식이 바뀐다.
- 맥락: 시험이 실제 시간을 기다리거나(요청 응답 대기 250ms·1000ms, 재개 대기 30ms, 설치 상한 20ms) 재서(지연 >= 35ms) 판정하면 기계가 바쁜 정도에 따라 결과가 바뀐다. 그 시험은 실패해도 결함이 아니고 통과해도 옳다는 뜻이 아니다.
- 결정: 컴포넌트(`link_public_api_send`, `link_staff_stream_receive`, `kiosk_flow`, `alert_sync`, `stt_adapter`)는 `setTimeout`·`Date.now`를 직접 부르지 않고 시계·타이머(`now`, `sleep`, `timers`)와 값(`timeoutMs`, `installTimeoutMs`)을 인자로 받는다. 기본값은 컴포넌트 안에 두지 않는다(빠지면 타입 오류). 실제 시계는 `src/wiring/clock.ts`(전역 타이머를 쓰는 유일한 파일)가, 값은 `src/config.ts`가 정하고 wiring 팩토리(`createPublicApiClient` 등)가 넣는다. 시험은 가짜 시계(`fakeTimers`)를 넣고 시간을 직접 흘린다.
- 왜: 의존성 주입이 시간을 시험하는 표준 방식이다(functional core / imperative shell, 포트·어댑터: DESIGN.md 2절). 판정은 결과(오류 종류·재시도 여부)이고 실제로 기다리는 시간은 0이다.
- 검토한 대안: (1) 전역 시계를 시험에서 덮어쓰기(`mock.timers`, 가짜 시계 라이브러리) -> 시험이 전역 상태를 건드리고, 코드가 어느 시계를 읽는지 타입으로 드러나지 않는다. 컴포넌트가 직접 읽는 것을 정적으로 막을 수 없다. (2) 시한을 늘려 덜 깨지게 -> 판정이 여전히 기계 속도에 달린다. (3) 시험을 그대로 두고 부하 반복 -> 같은 이유로 기각.
- 결과: 얻는 것 — 시험 중 실제 시간 0, 컴포넌트의 시간 의존이 인자로 보인다(`test/timing.test.ts`가 컴포넌트의 직접 시계 사용 0을 강제). 감수하는 것 — 컴포넌트 생성자 인자가 늘고 wiring이 기본을 채운다. 와이어 형식·HTTP 응답은 바뀌지 않았다(기존 시험 통과로 확인, `test/TIMING.md`).
- 되돌리는 조건: 없음. 시계가 더 필요한 컴포넌트가 생기면 같은 방식으로 인자를 추가한다.
