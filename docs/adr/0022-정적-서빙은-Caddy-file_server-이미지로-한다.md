# ADR 0022: 정적 서빙은 Caddy file_server 이미지로 한다

## 상태
채택됨 (2026-10-29, 단위 4a, D111). ADR 0010(의존 없는 Node 서버)을 대체한다(Supersedes 0010).

## 맥락
`server/static.mjs`(약 50줄)가 경로 정규화, 보안 헤더, `/healthz`·`/readyz`, `/config.json`, 로그, 종료 처리를 직접 했다. 표준 정적 서버가 있는데 직접 만든 것이다(표준성 점검 #45, 헤드가 O로 볼 여지를 남긴 항목). 헤드 결정 D111: 직접 만든 인프라를 표준 도구로 바꾼다.

## 결정
- 최종 이미지는 `caddy:2.11.7-alpine`(태그 고정, 2026-10-29에 받은 digest `sha256:eb4d35b7452d1ab6171fbdbe8d9275b2301dad6dad92115d91e19fb9b24d510f`)이고, 빌드 스테이지가 만든 `dist`와 `Caddyfile`만 담는다. 사용자는 `app`(uid 10001, root 아님).
- 동작은 `Caddyfile`의 설정으로 얻는다: 보안 헤더(`secure_headers` 조각, 오류 응답에도 `handle_errors`로 같은 조각), `/healthz`, `/readyz`(`file` 매처로 index.html 존재 확인, 없으면 503), `/config.json`(`CONFIG_FILE`을 서빙, 없으면 404), `/staff`의 301, GET/HEAD 외 405, JSON 접근 로그(요청 헤더·쿼리 문자열·`/healthz`·`/readyz` 제외).
- 지운 것: `server/static.mjs`, `server/static.d.mts`, 이를 시험하던 `test/static.test.ts`의 핸들러 시험 3개. 같은 성질은 실제 이미지를 띄워 `test-image/static-image.test.ts`(`npm run test:image`)가 확인한다.
- 개발·시험용 대역 `mock-server/devstatic.ts`(약 30줄)가 남는다. 이미지에는 들어가지 않고, 모의 서버 시연·jsdom 앱 시험·브라우저 시험이 `dist`를 같은 출처로 내는 데만 쓴다. 보안 헤더는 `Caddyfile`에서 읽어 와서 브라우저 시험이 실제 CSP 아래에서 돈다(헤더 목록은 한 곳).

## 왜
- 정적 서빙·헤더·종료·로그는 해결된 문제이고 Caddy는 그 표준 구현이다. 직접 구현은 경로 탈출, 인코딩, 느린 연결 같은 경계 처리를 우리가 계속 책임져야 했다.
- Caddy를 nginx보다 고른 이유: 설정이 짧고(한 파일) 환경 변수 치환(`{$PORT:8080}`)과 정지 시 진행 중 요청을 마치는 grace period가 기본이다. 헤드 지시(D111)가 Caddy file_server를 정했다. nginx와 직접 비교한 측정은 하지 않았다.
- 값(출처): `read_header 10s`, `idle 60s`: 느린 클라이언트 방어로 둔 값이고 **측정하지 않았다**(Caddy 기본값은 read_header 무제한이라 상한을 둔다). 기존 Node 서버는 Node의 기본값(`headersTimeout` 60s 등)이었다. `grace_period 10s`: Docker stop의 기본 대기 10초(제약). `protocols h1`: 앞단 게이트웨이가 평문 HTTP/1.1로 프록시한다는 구성의 가정이며 실제 게이트웨이는 확인하지 못했다.
- `Cache-Control: no-store`, CSP 등 헤더 값은 ADR 0010과 감사 P15에서 그대로 옮겼다(값을 바꾸지 않았다).

## 검토한 대안과 버리는 이유
- Node 서버 유지: 표준 도구가 있는데 직접 유지하는 비용을 계속 낸다(D111).
- nginx: 위 근거. 동등하게 가능했을 것이다.
- Caddy를 게이트웨이(deploy)에서만 쓰고 이미지는 정적 파일만 내보내기: CR-001이 열어 둔 선택이고 deploy의 결정이다. 이 이미지는 독립 시험·`/healthz`·`/readyz` 계약을 지켜야 하므로 자체 서빙을 유지한다.

## 결과
- 얻는 것: 직접 만든 정적 서버 코드와 그 시험 유지가 사라진다. 헤더와 로그가 설정 파일 한 곳에 있다.
- 동작 차이(보고 대상):
  1. **잘못된 퍼센트 인코딩(`/%zz`)의 400에는 보안 헤더가 붙지 않는다.** Go의 HTTP 파서가 요청 줄을 거부하면 Caddy 설정이 실행되기 전에 고정 응답(`400 Bad Request`, text/plain, 입력을 되풀이하지 않음)을 낸다. 전에는 헤더가 붙었다. HTML이 아니라 스크립트 실행 경로는 없다고 판단했지만 브라우저가 이 응답을 어떻게 다루는지는 실측하지 않았다.
  2. 경로 탈출 시도(`/../`)의 상태 코드가 403 대신 Caddy의 정규화 결과(파일 없음 404 또는 정규화)가 된다. 어느 쪽도 파일을 내지 않는 것을 시험한다.
  3. `PORT`가 정수가 아니면 종료 코드가 2가 아니라 Caddy의 비0 코드(1)다. 시작은 거부한다.
  4. 접근 로그의 키 이름이 `path`에서 `request.uri`로 바뀌었다(`scripts/smoke.sh` 검사를 갱신했다). Caddy 런타임 로그도 같은 표준 출력에 JSON으로 나온다.
  5. 이미지 크기와 시작 시간은 측정하지 않았다.
- 감수하는 것: 기본 이미지 의존이 Node에서 Caddy로 바뀐다(태그 고정, 갱신은 의도한 변경으로). 기기 설정 파일은 컨테이너 사용자(uid 10001)가 읽을 수 있어야 한다.

## 되돌리는 조건
게이트웨이가 정적 서빙을 맡기로 CR-001이 정해지면 이 이미지는 정적 파일만 담는 방식으로 줄일 수 있다. 400 응답에 보안 헤더가 필요하다고 판단되면(보안 검토) 앞단(게이트웨이)에서 붙인다.
