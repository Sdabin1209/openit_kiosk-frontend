# ADR 0015: 키오스크 대화 목록은 메모리 전용의 별도 컴포넌트(chat.ts)로 둔다

## 상태
채택됨 (2026-10-28, 지시서 2 데모 요구).

## 맥락
키오스크 화면은 서버가 준 최신 응답 문장 하나만 보였다(환자 발화는 되돌려 보이지 않았다). 데모에서는 현재 세션의 환자 발화와 시스템 응답이 시간순 말풍선으로 보여야 한다. 이 영역의 원칙은 환자 발화를 브라우저 메모리에만 두고 저장소·쿠키·콘솔에 남기지 않는 것이다(README, ADR 0006).

## 결정
1. `apps/kiosk/chat.ts`의 `ChatLog`가 대화 목록 컴포넌트다. 입력은 `ConversationEvent`(PATIENT, SYSTEM, CLEAR), 출력은 `ChatView`(말풍선 배열)뿐이다. 상태 기계·API·DOM을 모른다.
2. 상태 기계(`flow.ts`)는 이벤트를 `subscribeConversation`으로 내보내기만 하고 대화 내용을 저장하지 않는다. 환자 발화는 서버로 보내는 시점에, 시스템 응답은 응답을 받은 시점(시작·턴·재개 문장)에 낸다. 상태가 IDLE 또는 ENDED가 되면(종료, 처음 화면, 세션 만료) CLEAR를 낸다.
3. `chatview.ts`는 `ChatView`를 DOM에 그린다. 글자는 `textContent`로만 넣는다.
4. 말풍선 id(환자는 turn_id, 시스템은 `<turn_id>:r` 등)로 같은 말풍선의 중복을 막는다.
5. 말풍선은 최대 `MAX_BUBBLES`(100)개만 둔다.

## 왜 (따른 표준과 근거)
- 구조 규칙 R2~R5: 컴포넌트는 자기 입력·출력 스키마만 안다. 이벤트와 뷰 모델은 `chat.ts`에 타입으로 한 곳에 정의돼 있다. 기존 `KioskView` 뷰 모델 방식과 같은 모양이다.
- 저장하지 않는 이유: 영역 원칙(환자 발화는 메모리에서만). 세션이 끝나면 지워 다음 환자에게 남지 않게 한다(유휴 초기화와 같은 이유, ADR 0008).
- `aria-live="off"`: 최신 응답 문장은 기존 `#app`(aria-live polite)이 이미 읽어 준다. 목록까지 읽으면 같은 말이 두 번 낭독된다.
- 상한 100: 임의 값이며 측정하지 않았다. 목적은 긴 세션에서 메모리가 무한히 커지지 않게 하는 안전 상한이다. 초과 시 가장 오래된 것을 버린다.

## 검토한 대안과 버리는 이유
- `KioskView`에 대화 배열을 넣기: 화면 상태와 이력이 섞이고 `patch`마다 배열이 복사된다. 컴포넌트 경계가 사라진다.
- 서버의 StaffSessionView로 대화를 읽기: 키오스크 토큰으로는 직원 경로를 못 읽고, 환자 화면에 이웃 데이터를 가져오는 결합이 생긴다.
- 화면(main.ts)에서 DOM에 직접 덧붙이기: 시험이 브라우저 없이는 안 되고 지움 시점이 흩어진다.

## 결과
얻는 것: 대화가 보인다. 컴포넌트 시험(`test/chat.test.ts`)과 앱 전체 jsdom 시험(`test/kiosk-app.test.ts`)이 있다. 감수하는 것: 응답이 화면 전환보다 먼저 말풍선으로 들어간다(순서는 시간순 그대로). 서버가 `response_text`를 주지 않은 턴(null)은 말풍선이 없다.

## 되돌리는 조건
환자 화면에 대화 이력을 보이지 않기로 하면 `subscribeConversation` 연결(main.ts)만 끊으면 된다. 상한이 현장에서 맞지 않으면 값을 바꾸는 새 ADR로 대체한다.
