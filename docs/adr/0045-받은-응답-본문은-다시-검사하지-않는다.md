# ADR 0045: 받은 응답 본문은 다시 검사하지 않는다 (ADR 0005 대체)

## 상태
채택됨 (2026-11-09, 계약 v5.0.1). Supersedes: ADR 0005(응답 검증을 읽는 쪽 스키마로 한다).

## 맥락
`link_public_api_send`는 받은 FrontendInput·SessionState 등을 영역 안 사본 스키마(`FrontendBody`, `StartedBody`, `SessionStateBody`, `StaffCallRetryBody`, `StaffAlertBody`, `QuestionSetListBody`)로 다시 검사하고 어기면 일시 장애처럼 재시도했다. 사본이 응답 필드·열거값을 따로 정의해 계약·문진 스키마와 어긋날 수 있었다.

## 결정
생산자가 보증하는 DTO는 받는 쪽이 다시 거부하지 않는다(R7, ADR 0010). 유지하는 것: 본문 JSON 해석 실패(`BadBodyError`)·전송 실패·상태 코드 분기의 재시도와, 응답 `turn_failure_signal.write_committed=NOT_COMMITTED`(직원 호출 판단 뒤 같은 turn_id 재시도)라는 업무 분기. 자체 사본 스키마 6개와 예시를 지우고 타입은 생성물을 쓴다.

## 왜
- R7: 컴포넌트가 낸 값은 받는 쪽이 다시 검증하지 않는다. D117: 같은 뜻의 정의는 한 번만.
- 모양이 틀린 응답을 재시도해도 같은 응답이 올 가능성이 높고, 환자 턴만 지연된다.

## 검토한 대안과 버리는 이유
- 사본 유지(관대한 읽기): 정의가 둘이다. 버린다.
- 계약 스키마로 위임해 검증: 여전히 다시 거부한다. 계약 위반은 생산자의 결함이고 이 영역이 가릴 일이 아니다.

## 결과
- 얻는 것: 정의 한 곳. 감수하는 것: 생산자가 모양을 어기면 화면 코드가 해당 칸을 읽다 오류가 나 시작·턴 실패 경로(직원 호출)로 간다(재시도 아님).
- `GET /v1/question-sets` 응답은 계약에 스키마가 없어 `QuestionSetItem` 타입만 코드에 있다(PUBLIC_API.md I절 산문). 계약에 스키마가 생기면 생성 타입으로 바꾼다(변경 요청 사항).

## 되돌리는 조건
계약이 응답 검증을 읽는 쪽 책임으로 정하면 그 스키마에 위임해 다시 도입한다.
