# ADR 0001: 프레임워크 없는 TypeScript와 esbuild 번들

## 상태
채택됨 (2026-10-28 작성. 기존 결정은 코드·docs·git log에서 근거를 찾아 적었고, 근거를 못 찾은 곳은 '근거 기록 없음'이라 표시했다)

## 맥락
화면이 단순하다(키오스크는 한 화면에 한 가지 행동, 직원 콘솔은 목록과 대화상자). 브리프 7절은 "TypeScript와 빌드 도구(Vite 등)를 권장하나 영역이 정한다, 의존은 최소"라고 했다. 이 영역은 분리 가능한 가장자리 영역(D65)이라 실제 프론트팀이 통째로 바꿀 수 있어야 한다.

## 결정
프레임워크(React 등) 없이 TypeScript + DOM, 번들러는 esbuild 하나(`scripts/build.mjs`, iife, minify, target es2022). 시험은 `node:test`(Node 24 타입 제거 지원).

## 왜 (따른 표준과 근거)
- 따른 기준: 브리프 4·5절의 '의존 최소·번들 작게·외부 CDN 금지·오프라인', 런타임 의존 0.
- 근거(확인한 것): 빌드 산출물이 `dist/kiosk.js` 약 12KB, `staff.js` 약 14KB이고 런타임 의존이 없다(감사 문서가 `dist`를 확인).
- 근거 기록 없음: 프레임워크·Vite를 직접 비교한 기록은 리포지토리와 git log에 없다. 위 선택은 설계서 7절 한 줄("번들은 작게, 의존은 최소. 화면이 단순하다")이 전부다.

## 검토한 대안과 버리는 이유
- React/Vue 등: 의존·번들이 커지고 보안 점검 표면이 늘어난다. 화면 상태가 `KioskFlow` 상태 기계 하나라 필요성이 작다고 보았다(비교 실측 없음).
- Vite: 브리프가 권장했으나 개발 서버·플러그인 의존이 늘고, 이 영역은 개발을 컨테이너 밖 Node에서 하고 산출물만 정적 파일이면 된다. 비교 기록 없음.

## 결과
UI가 상태를 직접 다루는 코드가 `main.ts`에 모인다(DOM 갱신을 손으로 한다). 화면이 복잡해지면 유지가 어렵다. 시험은 UI 없이 `flow.ts`를 대상으로 한다.

## 되돌리는 조건
화면이 지금의 몇 배로 복잡해지거나 실제 프론트팀이 프레임워크로 맡을 때. 그때는 `api/`와 `apps/kiosk/flow.ts`(UI를 모른다)를 재사용하고 UI만 바꾼다.
