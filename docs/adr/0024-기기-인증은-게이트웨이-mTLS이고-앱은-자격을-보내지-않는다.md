# ADR 0024: 기기 인증은 게이트웨이 mTLS이고 앱은 기기 자격을 보내지 않는다

## 상태
채택됨 (2026-10-29, 단위 4b, 계약 v2.3.0 PUBLIC_API.md F절, 헤드 ADR 0012·D113). ADR 0006(기기 토큰을 메모리와 설정 파일에 둔다)을 대체한다(Supersedes 0006).

## 맥락
이전에는 키오스크가 기기 토큰을 시작 URL 조각이나 `/config.json`으로 받아 `Authorization: Bearer`로 보냈다. 계약 2.3.0은 기기 인증을 게이트웨이의 클라이언트 인증서 검증(mTLS)으로 바꿨다. 브라우저가 TLS에서 인증서를 내고, 게이트웨이가 인증서 CN을 `X-Openit-Device`로 붙여 서비스에 넘긴다. 앱이 기기 자격을 다루지 않는다. 기기 토큰은 2.x 호환으로만 남고 3.0.0에서 없어진다.

## 결정
- 기기 토큰이 없어도 앱은 정상 동작한다. 이전의 "설정이 필요합니다" 화면(`NO_DEVICE_TOKEN`)과 그 문구, 호출 이유 값을 지웠다(필수 설정이 더는 없다). 서버 401·403은 그대로 "인증이 거부" 화면이다(게이트웨이가 인증서를 거부해도 같다).
- 토큰이 있으면(`/config.json`의 `device_token`, 조각 `#device=`) 2.x 호환으로 `/v1/sessions*`에 Bearer를 싣는다. 코드는 `api/client.ts`에만 있다. 3.0.0에서 이 경로를 지운다.
- 앱은 `X-Openit-Device`를 보내지 않는다(게이트웨이가 클라이언트가 보낸 값을 지우고 인증된 값을 붙인다).
- 모의 서버에 게이트웨이 흉내 모드(`gatewayDevice`, `MOCK_GATEWAY_DEVICE=<기기 ID>`)를 추가했다: `/v1/sessions*`에서 `X-Openit-Device`가 없거나 형식(`^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$`)이 틀리면 401, 다른 기기가 만든 세션은 404. 데모에서는 모의 서버 앞단이 헤더를 붙인다.
- 생성 검증기를 계약 v2.3.0에서 다시 만들었다(`device_token`은 deprecated로 선택 그대로).

## 왜
- 계약이 정했다(D113). 근거와 대안 비교는 헤드 ADR 0012에 있고 이 영역은 따르기만 한다. 브라우저가 비밀(토큰)을 갖지 않으면 메모리 보관 규칙(ADR 0006)과 `/config.json`에 비밀이 실리는 문제(표준성 점검 #12~#14)가 사라진다.
- 토큰 경로를 바로 지우지 않은 이유: 계약이 2.x 동안 토큰 방식도 받는다고 했고, 게이트웨이와 서버가 전환되기 전 환경에서 앱이 깨지지 않게 하려는 것이다.

## 검토한 대안과 버리는 이유
- 토큰 경로를 지금 지우기: 3.0.0 계약 전이고 아직 mTLS 게이트웨이가 확인되지 않았다.
- 토큰이 없으면 계속 설정 필요 화면: mTLS에서는 토큰이 없는 것이 정상이라 모든 기기가 막힌다.

## 결과
- 얻는 것: 앱이 기기 비밀을 다루지 않는다. 토큰 없는 설정으로 세션이 시작~종료된다(`test/mtls.test.ts`, 브라우저 시험).
- 감수하는 것: 실제 게이트웨이의 mTLS와 인증서 거부 시의 응답(401인지 TLS 단계 거부인지)은 확인하지 못했다. TLS 단계에서 거부되면 브라우저는 요청 자체가 실패해 앱은 네트워크 오류로 보고 재시도 예산 뒤 직원 호출 화면을 보인다. 인증서 발급·갱신·폐기는 이 영역 밖이다.

## 되돌리는 조건
계약 3.0.0에서 토큰 방식이 없어지면 `device_token`, `#device=`, Bearer 경로를 지운다.
