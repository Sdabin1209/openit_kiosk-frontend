# 0035. 응답 대기 60초, 재시도 총 예산 120초, 대기 화면 피드백 1초·10초 (0033의 값을 대체)

- 상태: 채택 (2026-11-02, 사용자 결정 D125). Supersedes: [0033](0033-응답-대기-12초와-재시도-총-예산-24초.md)의 값 부분(대기 12초, 예산 24초). 예산 = 대기의 2배라는 원칙과 백오프 구조는 유지.
- 맥락: "응답 2초는 목표지만 2~3초 넘었다고 전부 실패시키는 건 맞지 않다." 대기 12초는 목표를 상한으로 쓴 값이었고, 첫 호출의 JIT 컴파일 같은 정상 지연에도 턴이 실패했다(계약 CONVENTIONS 시간 상한 사슬, H4 실측 2026-11-02). 계약이 사슬을 키오스크 60 > gateway 1+55 > survey 50으로 개정했다.
- 결정: `REQUEST_TIMEOUT_MS = 60_000`, `DEFAULT_RETRY.budgetMs = 120_000`(`src/config.ts`). 직원 콘솔도 같은 클라이언트라 같은 60초다(gateway 직원 경로 56초보다 길다). 화면 피드백: SENDING 진입 1초 뒤 `KioskView.waitHint = THINKING`("생각하고 있어요..."), 10초 뒤 `PLEASE_WAIT`("조금만 더 기다려 주세요."). 상수 `WAIT_PROGRESS_MS = 1_000`, `WAIT_NOTICE_MS = 10_000`, 문구는 `patient_copy.ts`. 이전에는 대기 중 진행 표시가 없었다(제목 "확인하고 있어요"만 있었음): 새로 만들었다.
- 왜: 60초는 HTTP 프록시·부하분산기의 표준 기본 상한(nginx `proxy_read_timeout` 60초, AWS ALB idle timeout 60초)이다. 1초·10초는 Nielsen 응답 시간 지침(1초: 흐름이 끊겼음을 알리는 진행 표시, 10초: 주의 유지 한계에서 안내)이다. 예산 120초는 0033과 같은 비례(대기의 2배: 한 번 기다린 뒤 한 번 더 시도)이며 측정이 아니라 이전 선택의 연장이다. 백오프 상한 5초는 쉬는 시간 하나의 상한이라 예산과 무관하게 둔다. 값은 모두 측정하지 않았다.
- 검토한 대안: (1) 대기 12초 유지 -> 정상 지연에도 실패(D125가 거부). (2) 예산 60초(재시도 없음) -> 재시도로 일시 장애를 넘기는 성질을 잃는다. (3) 피드백 타이머를 컴포넌트가 직접 읽는 시계로 -> ADR 0034 위반, 시험이 실제 시간을 기다리게 된다.
- 결과: 얻는 것 — 정상 지연이 실패가 되지 않고, 기다리는 환자가 진행·안내를 본다. 감수하는 것 — 서버가 응답하지 않을 때 환자가 직원 호출 화면까지 기다리는 최대 시간이 늘어난다(대기 60초, 예산 120초; 중간에 환자가 직원 호출 버튼을 누를 수 있다: 재시도 중 화면). 임상 현장에 맞는지는 확인하지 못했다. 피드백 문구는 임상 검토 전 임시 UI 문구다.
- 되돌리는 조건: 계약의 시간 상한 사슬이 다시 바뀌면 새 ADR로 대체한다.
